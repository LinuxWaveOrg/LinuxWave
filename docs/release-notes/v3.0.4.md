# 安全更新

**LinuxWave 3.0.4** · Build number: **291G2008**

> 建议所有用户升级。这次修的是一个**完整性校验缺失**的问题：没有校验值的包会被直接安装并执行。

## 问题

3.0.3 及之前，如果索引记录里**没有 `sha256` 字段**，安装器只打印一条黄色警告，然后照常下载并安装：

```
🌊 Warning: No SHA256 provided, skipping verification.
🌊 Successfully installed ...
```

索引记录是整条信任链的起点。每条记录声明「这个 URL 对应的内容，其 SHA-256 是 X」，安装时把下载到的字节与 X 比对，是**唯一**把「索引承诺的内容」与「实际落盘的内容」绑在一起的动作。

HTTPS 只保护传输过程，它保护不了两件事：

- 索引本身被改动（例如有人往索引里加一条记录）
- 上游替换同名产物

一旦缺少 X，这两种情况都无从发现 —— 装进来什么，就会被直接执行。

## 修复

三个层次全部拒绝：

| 层次 | 位置 | 行为 |
| --- | --- | --- |
| 软件包记录 | `pkg/pkginstaller.py` | 缺 `sha256` 或格式非法 → 报错退出，**下载之前**就停下 |
| 依赖记录 | `surfboard/depsinstaller.py` | 同上 |
| 安装核心 | `surfboard/depsmanager.sh` | 最后一道防线，同样拒绝 |

同时要求校验值必须是 **64 位小写十六进制**。以前即使字段存在、但格式不对（长度不足、含大写、混入非十六进制字符），也要走到比对阶段才失败，报错既晚又难懂。

## 影响面

LinuxWave 索引里的 **112 条版本记录**全部带合法校验值，所以这次收紧**不影响任何正常安装**。

唯一行为变化的是故意做坏的 `test_no_sha256` 测试夹具 —— 它存在的意义正是验证这条分支，现在它验证的是「必须拒绝」。

`test_wrong_sha256` 不受影响：它的校验值格式合法、只是内容错误，仍然由原有的「比对不一致」分支拦下（报错并删除已下载的损坏文件）。

## 新增：校验值回归测试（防止这条行为被改回去）

修复本身只有几十行，**风险在于将来被悄悄改回去而无人察觉**。此前没有任何测试盯着它：
`format_test.sh` 只跑 `test_bin_*`，而从 MacWave 搬过来的 `test/test_no_sha256` /
`test/test_wrong_sha256` 两个夹具文件在 LinuxWave 里**没人引用**，是闲置的。

新增 `scripts/checksum_test.sh`，三段：

1. **离线**测校验核心 `mw_verify_sha256` 的行为（上表那六种输入）；
2. **端到端**装两个坏夹具，断言失败文案正确且不留下安装痕迹；
3. **静态哨兵**：三处守卫的报错文案缺一即失败 —— 数据里没有「缺校验值的**依赖**」夹具，那一层没有外部行为可测，只能靠哨兵防重构时被删。

网络不可达时第 2 段记 **SKIP 而非 FAIL**（连不上与「被拒绝」是两件事）。

**这条测试确实能抓住回归**：在部署了 3.0.3 旧代码的树上跑，第 2 段当场 3 条 FAIL
（`test_no_sha256` 竟然装成功了）；把新代码部署进假根后再跑，26 PASS / 0 FAIL / 0 SKIP。

## 一并包含：审计判据与安装器对齐

`scripts/audit_deps.py` 原来对缺 `sha256` 只报「安装器会跳过校验」的**警告**。安装器现在会拒绝，所以判据跟着改：

- **真实软件包**缺 `sha256` → 判为 problem、退出码 1（这条记录会让安装必然失败，属于数据缺陷）；
- **`test_*` 夹具**留空 → 仍是警告（`test_no_sha256` 就是为了验证拒绝分支）。

反证过：删掉 `tree@2.3.2` 的校验值后审计报 problem、退出码 1。

## 一并包含：夹具不再跨组织引用

`test_no_sha256` / `test_wrong_sha256` 的 `url`、`home` 与作者此前都指向 **MacWave** ——
这两条记录是从 MacWave 的数据里搬过来的，落地时没跟着改。后果是校验值回归测试要跨组织拉别人的仓库，MacWave 一旦删掉或改名就会断。现在四个记录（两个夹具 × 两个架构）都指向本项目自己的 `test/` 目录。

## Security update

**LinuxWave 3.0.4** · Build number: **291G2008**

> All users are advised to upgrade. This release fixes a **missing integrity check**: a package without a checksum was installed and executed all the same.

### The problem

Up to 3.0.3, when an index record had **no `sha256` field**, the installer printed a yellow
warning and went ahead with the download and the install:

```
🌊 Warning: No SHA256 provided, skipping verification.
🌊 Successfully installed ...
```

An index record is the root of the whole trust chain. Each record states "the content behind
this URL has SHA-256 X", and comparing the downloaded bytes against X is the **only** action
that ties "what the index promised" to "what actually landed on disk".

HTTPS protects the transfer, not two other things:

- the index itself being modified (somebody adding a record, for instance);
- the upstream replacing an artifact under the same name.

Without X neither can be detected -- whatever arrives gets executed.

### The fix

All three layers refuse:

| Layer | Location | Behaviour |
| --- | --- | --- |
| Package record | `pkg/pkginstaller.py` | missing or malformed `sha256` → error and exit, **before the download** |
| Dependency record | `surfboard/depsinstaller.py` | same |
| Install core | `surfboard/depsmanager.sh` | the last line of defence, same refusal |

The checksum must also be **64 lowercase hexadecimal characters**. Previously a field that
existed but was malformed (too short, uppercase, non-hex characters) only failed at the
comparison stage, which is both late and hard to read.

### Impact

All **112 version records** in the LinuxWave index carry a valid checksum, so the tightening
**does not affect any normal install**.

The only behavioural change is the deliberately broken `test_no_sha256` fixture -- its reason
to exist is to exercise exactly this branch, and it now verifies that the installer refuses.

`test_wrong_sha256` is unaffected: its checksum is well-formed and merely wrong, so the
existing "mismatch" branch still catches it (error out and delete the corrupted download).

### Measurements

Results from `scripts/checksum_test.sh` against the **fixed** code:

| Input | Expected | Exit code | Message |
| --- | --- | --- | --- |
| empty checksum | refuse | 1 | `No SHA256 checksum ... refusing to install` |
| `abc` (too short) | refuse | 1 | `Malformed SHA256 checksum ... Expected 64 lowercase hexadecimal` |
| 64 chars with uppercase | refuse | 1 | same (malformed) |
| 64 non-hex characters | refuse | 1 | same (malformed) |
| well-formed but wrong | fail and delete the file | 1 | `SHA256 verification failed. Removing corrupted file.` + file gone |
| correct 64 lowercase hex | pass | 0 | `SHA256 verification passed!` |

End to end (installing the real broken fixtures):

| Target | Expected | Measured |
| --- | --- | --- |
| `test_no_sha256@1.0.0` | refused, nothing left behind | exit 1, no trace in `bin/` or `links/` |
| `test_wrong_sha256@1.0.0` | refused, nothing left behind | exit 1, no trace in `bin/` or `links/` |

### New: a regression test so this cannot silently come back

The fix itself is a few dozen lines; **the risk is it being quietly reverted later**. Nothing
watched it before: `format_test.sh` only covers `test_bin_*`, and the `test/test_no_sha256` /
`test/test_wrong_sha256` fixtures carried over from MacWave were **unreferenced** in LinuxWave.

`scripts/checksum_test.sh` has three parts:

1. **offline** behaviour of the checksum core `mw_verify_sha256` (the six inputs above);
2. **end to end** installs of the two broken fixtures, asserting the right message and that
   nothing is left behind;
3. a **static sentinel** over the three guard sites -- the data has no "dependency without a
   checksum" fixture, so that layer has no external behaviour to test and only a sentinel can
   catch it being deleted during a refactor.

When the network is unreachable part 2 records **SKIP, not FAIL** -- "cannot connect" and
"refused" are different outcomes.

**The test genuinely catches the regression**: run against a tree still running the 3.0.3 code,
part 2 produced 3 FAILs on the spot (`test_no_sha256` installed successfully); with the fixed
code deployed into a fake root it reports 26 PASS / 0 FAIL / 0 SKIP.

### Also included: the audit now agrees with the installer

`scripts/audit_deps.py` used to treat a missing `sha256` as a **warning** ("the installer will
skip verification"). The installer refuses now, so the criterion follows:

- a **real package** without `sha256` → a problem, exit code 1 (that record makes installation
  fail, so it is a data defect);
- a **`test_*` fixture** left empty → still a warning (`test_no_sha256` exists to verify the
  refusal branch).

Proven in the negative direction: deleting the checksum from `tree@2.3.2` makes the audit
report a problem and exit 1.

### Also included: the fixtures no longer point at another org

`test_no_sha256` / `test_wrong_sha256` had `url`, `home` and author pointing at **MacWave** --
the records were carried over from MacWave's data and never adjusted. The consequence was that
the checksum regression would pull from another org's repository, and would break the day
MacWave renamed or removed those files. All four records (two fixtures × two architectures) now
point at this project's own `test/` directory.
