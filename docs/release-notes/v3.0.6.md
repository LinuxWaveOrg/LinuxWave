# LinuxWave 3.0.6

Build number: **296E1356**

**本次为兼容更新：3.0.5 装过的用户可以直接 `wave selfupdate` 升到 3.0.6，不需要重装。**

> 3.0.6 是**过渡版本**：3.1.0（自带 Python，`wave` 不再依赖系统解释器）正在准备中，
> 所以本次**只更新 `configdata` 的版本数据，不改 README 与官网** —— 站点上的版本号
> 会在 3.1.0 发布时一次性刷到 3.1.0。`wave -V` 与 `configdata` 都会如实显示 3.0.6。

## 修复：一次网络抖动不再让整轮自更新前功尽弃

3.0.5 及之前，逐文件下载是**单次 `curl`** —— 连 `--max-time` 都没有：

```bash
run_cmd curl -fsSL -o "$BASE_DIR/$local_path" "$BASE_URL/$repo_path"
```

链路一重置就整轮失败。这不是假设，是实测过的：

```
$ wave selfupdate
🌊 Updating LinuxWave from 3.0.1 to 3.0.5...
curl: (35) Recv failure: 连接被对方重置
🌊 Error: The update did not complete (still on 3.0.1).
```

失败时机还特别难受：文件已经下了一半、目录里留下了新旧混杂的代码，用户只能整轮重跑，
而网络不好时下一轮很可能再失败一次。

### 修复

新增 `fetch_to_file()`（与 MacWave 3.1.0 同构）：

- **每个请求都有超时**：`FILE_TIMEOUT=180` 秒（元数据 30/60 秒），真挂住的连接不会把整轮拖死；
- **失败重试 3 次**（`FETCH_ATTEMPTS=3`），间隔 2 秒；
- **先写 `<目标>.linuxwave-part` 再 `mv`**：重试期间目标位置不会出现半个文件，
  全部失败时**原地那份好文件也不受影响**；
- **按 curl 退出码 + HTTP 状态码判断值不值得重试**：4xx 与 22/23/1~3 直接放弃。
  这条很关键 —— `raw.githubusercontent` 在 404 时常常报 `(56)` 收数据失败而不是 `(22)`，
  只看退出码会把「这个文件不存在」当成网络抖动，白等三次。

三处调用点都换了过来：**文件列表**、**逐文件更新**、**直接调用时取版本号**。
顺带把文件列表那段自带的重复重试循环收敛到同一个函数 —— 原先有两套重试实现，
迟早会走偏。

失败时的提示也不一样了：直接点名是**哪个文件**没下成，并说明 `VERSION.json` 未被改动、
网络恢复后重跑即可。

## Fix: one network hiccup no longer discards a whole self-update

Up to 3.0.5 each file was fetched with a **single `curl`** call -- without even a
`--max-time`:

```bash
run_cmd curl -fsSL -o "$BASE_DIR/$local_path" "$BASE_URL/$repo_path"
```

A reset link failed the whole run. This is not hypothetical; it was measured:

```
$ wave selfupdate
🌊 Updating LinuxWave from 3.0.1 to 3.0.5...
curl: (35) Recv failure: Connection reset by peer
🌊 Error: The update did not complete (still on 3.0.1).
```

The timing is what hurts: half the files were already replaced, the tree holds a mix of old
and new code, and the only way forward is to run the whole thing again -- which, on a bad
link, is likely to fail again.

### The fix

A new `fetch_to_file()` (structurally the same as MacWave 3.1.0):

- **every request has a timeout**: `FILE_TIMEOUT=180` seconds (30/60 for metadata), so a truly
  stuck connection cannot hang the run forever;
- **three attempts** (`FETCH_ATTEMPTS=3`) with a 2-second delay;
- **writes `<dest>.linuxwave-part` and then `mv`s it**: during retries the destination never
  holds a half file, and when everything fails **the good file already in place is untouched**;
- **decides whether a retry is worthwhile from the curl exit code *and* the HTTP status**:
  4xx and 22/23/1--3 give up immediately. This matters -- on 404 `raw.githubusercontent` often
  reports `(56)` (receive failure) rather than `(22)`, so exit code alone would treat "this file
  does not exist" as a transient hiccup and wait through three pointless attempts.

All three call sites now use it: **the file list**, **each file update**, and **fetching the
version number when the script is invoked directly**. The file-list step had its own retry loop,
which was folded into the same helper -- two retry implementations were bound to drift apart.

The failure message also changed: it names the **file** that could not be downloaded and states
that `VERSION.json` was left unchanged, so re-running once the network recovers is enough.

## Measurements

`fetch_to_file` was extracted and driven on its own (`RETRY_DELAY` set to 0 so the test does not
actually wait):

| Case | Exit code | Time | Note |
| --- | --- | --- | --- |
| normal download (`lib/wave.py` from raw) | 0 | — | 3902 bytes, correct first line |
| **404** (missing path) | 1 | **1s** | no retry, as intended |
| **host unreachable** (`no-such-host.invalid`) | 1 | — | gives up after three attempts |
| **good file present + download fails** | 1 | — | file **byte-for-byte unchanged** (same SHA256) |
| all of the above | — | — | **no `.linuxwave-part` left behind** |

End to end (a `LINUXWAVE_TEST` fake root against the real network):

| Situation | Result |
| --- | --- |
| injected failure (raw unreachable) | three attempts → clean error → `VERSION.json` **untouched**, nothing left in the install tree |
| once the network recovered | `Retrying (2/3): …/lib/help.py` then continues with `lib/configerror.py` -- a single file no longer aborts the run |
| CI, both Pythons (3.14 / 3.15) | `Run selfupdate test` **success** on both legs (that step performs a real end-to-end self-update) |
