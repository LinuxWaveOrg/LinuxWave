# 重要更新

**LinuxWave 3.1.0** · Build number: **296E1439** · 发布于 **2026-10-29** · 发布分支：`3.1`

> 建议所有用户升级。这一版解决的是一个**结构性问题**：LinuxWave 不再依赖你自己装的那个 Python。

## 为什么要升级

3.0.x 及更早，`lib/wave` 是 `wave.py` 的副本，第一行是 `#!/usr/bin/env python3`，而三个依赖是用安装时那个 `pip3` 装进**当时那个**解释器的。两段「当时」一旦不一致，所有命令都会以「模块不可用」的形式失败。

**Linux 上这件事比 macOS 更容易撞上，而且更致命：**

| | macOS | Linux |
| --- | --- | --- |
| `python3` 换版本 | Homebrew 升级一次就换路径 | apt / pyenv / Homebrew / conda 都可能接管 |
| `pip3 install` 能否直接装 | 通常可以 | **现代 Debian/Ubuntu 受 PEP 668 保护，直接拒绝** |

实测（Ubuntu 26.04，系统 Python 3.14.4）：

```
$ pip3 install --dry-run requests
error: externally-managed-environment
hint: See PEP 668 for the detailed specification.
```

而 `install.sh` 是 `set -eE` + `trap install_failed ERR`，所以这一句失败就意味着**整次安装中止**。全新机器上甚至先撞「`pip3: command not found`」（`python3-pip` 默认不装）。

换句话说：**3.0.x 在一台干净的 Ubuntu/Debian 上装不上**，而现有用户靠的是「碰巧系统里已经有」这三个包（比如 apt 装了 `python3-requests`）。

## 环境要求（变了）

| | 3.0.x 及更早 | **3.1.0 起** |
| --- | --- | --- |
| Python | 必须自己装 3.14+，且要与 `pip3` 装依赖时的解释器一致 | **不需要装** |
| Linux | 任意 glibc 发行版 | 不变 |
| 磁盘占用 | — | 多约 111 MB（自带 CPython 3.14.9）＋ 32 MB（私有 venv） |
| 首次安装下载 | — | 多约 36 MB（amd64）/ 30 MB（arm64） |

## 这一版做了什么

**自带解释器。** 安装时从 `configdata/pythondata/latest_python` 读地址，下载 CPython **3.14.9**
（`python-build-standalone` 的 `install_only_stripped`，Linux 两架构），校验 sha256 后解到
`$BASE_DIR/python/<版本>/`，再建一个 `current` 符号链接。校验值由 CI 下载后自己重算比对，不采信上游自述。

**私有 venv。** 在安装根目录建 `venv/`，把 `requests` / `packaging` / `rich` 装进去 ——
从此与系统 Python 的升级彻底解耦。

**入口变成 sh 启动器。** `lib/wave` 不再是 `wave.py` 的副本，而是按顺序挑选**真正能 import 到依赖**的解释器，每一层都实测：

```
1. $BASE/venv/bin/python3           ← 正常就是它
2. $BASE/python/current/bin/python3 ← venv 坏掉时的第一选择
3. 安装时记录的解释器               ← 烘进启动器里
4. PATH 上的 python3                ← 最后兜底，wave.py 会明确指出缺哪个依赖
```

**降级路径（不会因为网络装不上）：**

- 自带解释器下载失败 → 回退系统 `python3`，安装继续，并提示网络恢复后重跑可让安装自足；
- venv 里装不上依赖 → 退回 `--system-site-packages` 的 venv（系统里已有这三个包时仍可用）；
- 两者都不行 → 如实失败，**不谎报安装成功**。

**`wave selfupdate` 也会补齐这套环境**，否则从 3.0.x 升上来的用户入口仍是旧的 python 副本。已存在的解释器与 venv 会复用，不会每轮重下 36 MB。

**新增依赖预检。** 绕过启动器直接 `python3 lib/wave.py` 时，缺依赖会直接点名缺哪个、当前解释器是谁、怎么修，而不是让某个子模块在导入阶段报一句「模块不可用」。

## 已知限制

- 首次安装/升级要多下 30–36 MB 的解释器。离线环境可先把对应架构的压缩包放到
  `$BASE_DIR/downloads/tmp/portable-python-<版本>.tar.gz`；
- 只提供 amd64 / arm64，**没有 universal 二进制**；
- 解释器来自上游归档，**上游清理旧 tag 时地址会失效** —— 这是本方案唯一的静默失效点，
  所以新增了每月一次的 CI 体检（`portable-python.yml`）：核对两个架构的地址与校验值、
  确认包里真有解释器、并真的用它建 venv 跑一遍 `wave`。

## Major update

**LinuxWave 3.1.0** · Build number: **296E1439** · Release branch: `3.1`

> All users are advised to upgrade. This release fixes a **structural** problem: LinuxWave
> no longer depends on the Python you happened to install.

### Why upgrade

Up to 3.0.x, `lib/wave` was a copy of `wave.py` starting with `#!/usr/bin/env python3`, and
the three dependencies had been installed by whichever `pip3` existed **at install time**. As
soon as those two "at the time" differ, every command fails with "module not available".

**On Linux this is both likelier and worse than on macOS:**

| | macOS | Linux |
| --- | --- | --- |
| `python3` changing | one Homebrew upgrade moves it | apt / pyenv / Homebrew / conda can all take over |
| `pip3 install` working directly | usually fine | **modern Debian/Ubuntu block it via PEP 668** |

Measured (Ubuntu 26.04, system Python 3.14.4):

```
$ pip3 install --dry-run requests
error: externally-managed-environment
hint: See PEP 668 for the detailed specification.
```

And `install.sh` runs under `set -eE` with a `trap install_failed ERR`, so that single failure
**aborts the whole install**. On a fresh machine it first hits "`pip3: command not found`"
(`python3-pip` is not installed by default).

In other words: **3.0.x cannot install on a clean Ubuntu/Debian box**, and existing users are
running on the luck of already having those three packages (say, from `python3-requests`).

### Requirements (changed)

| | 3.0.x and earlier | **3.1.0 onward** |
| --- | --- | --- |
| Python | you must install 3.14+, matching the `pip3` that installed the dependencies | **not needed** |
| Linux | any glibc distribution | unchanged |
| Disk | — | about 111 MB more (bundled CPython 3.14.9) plus 32 MB for the private venv |
| First install download | — | about 36 MB (amd64) / 30 MB (arm64) more |

### What this release does

**A bundled interpreter.** At install time the address is read from
`configdata/pythondata/latest_python`, CPython **3.14.9** is downloaded
(`install_only_stripped` from `python-build-standalone`, both Linux architectures), its sha256
verified, unpacked to `$BASE_DIR/python/<version>/`, with a `current` symlink. CI recomputes
the checksum itself instead of trusting upstream's word.

**A private venv.** `venv/` is created under the install root and `requests` / `packaging` /
`rich` go into it -- fully decoupled from system Python upgrades.

**The entry point becomes an sh launcher.** `lib/wave` is no longer a copy of `wave.py`; it
picks an interpreter that **can actually import the dependencies**, testing every layer:

```
1. $BASE/venv/bin/python3           <- normally this one
2. $BASE/python/current/bin/python3 <- first choice when the venv breaks
3. the interpreter recorded at install time
4. python3 from PATH                <- last resort; wave.py names the missing module
```

**Degradation paths (so a bad network never blocks an install):**

- bundled download fails → fall back to system `python3`, install continues, with a note that
  re-running once the network is up makes the installation self-contained;
- dependencies cannot be installed into the venv → fall back to a `--system-site-packages`
  venv (works when the system already has them);
- neither works → fail honestly, **never report a false success**.

**`wave selfupdate` also fills this in**, otherwise users coming from 3.0.x would keep the old
python copy as their entry point. Existing interpreters and venvs are reused, so it does not
re-download 36 MB every time.

**A dependency pre-check.** When `wave.py` is invoked directly (bypassing the launcher), a
missing dependency now names itself, shows the current interpreter and the exact fix, instead
of letting some submodule fail at import time with "module not available".

### Known limitations

- the first install/upgrade downloads a 30--36 MB interpreter; offline installs can pre-place
  the archive at `$BASE_DIR/downloads/tmp/portable-python-<version>.tar.gz`;
- only amd64 / arm64, **no universal binary**;
- the interpreter comes from an upstream archive, so **upstream removing an old tag breaks the
  URL** -- the single silent failure mode of this design, which is why there is now a monthly
  CI check (`portable-python.yml`): it verifies both architectures' URLs and checksums, confirms
  the archive really contains the interpreter, and builds a venv with it to run `wave`.
