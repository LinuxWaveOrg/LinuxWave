# Release Note 更新日志

**本次为兼容更新：3.0.1 装过的用户可以直接 `wave selfupdate` 升到 3.0.2，不需要重装。**

构建号：**284G2306**

## 共享安装：安装完成时就告诉用户怎么让组生效

3.0.2 之前，安装器只在**出错时**才提「加入组后要重新登录」。而实际上在 systemd 桌面环境里，**重新登录往往并不够** —— 于是用户会以为安装坏了。

原因：图形会话里的进程（`gnome-shell`、终端、编辑器）通常不是由登录会话直接拉起的，而是由 `systemd --user` 这个**用户管理器**拉起的。它会跨越注销存活（尤其在「注销后很快又登录」时，停止它的动作会被取消），因此一直握着**加入组之前**的凭据集合。结果：

```
wave install <包名>
🌊 Error: No write permission for the LinuxWave install tree.
```

重登之后依然如此 —— 因为父进程没换过。

3.0.2 起，三处输出都会给出下一步：

- `lib/install.sh` —— **安装完成后的收尾提示**（本版新增，用户不必先撞一次错）
- `lib/selfupdate.sh` —— 自更新收尾提示（共享树同样会被交给组）
- `pkg/pkginstaller.py` —— `print_write_permission_advice()`，即报错时看到的提示

内容是：若重登后仍不可写，说明首次登录时启动的用户管理器还握着旧凭据，请执行

```
systemctl --user exit
```

然后重新登录（重启亦可）。

这不是新引入的概念：`lib/uninstall.sh` 删除 `linuxwave` 专用账号时**早就在用**同一手法（先 `systemctl stop user@<uid>.service`，否则 `userdel` 会以「用户被进程使用」拒绝）。

官网与 README（中英文）的共享安装说明也同步补上了这一句。

## 新增：在假根里安全地跑整个程序（`LINUXWAVE_TEST`）

端到端会装包、改配置、删目录，以前只能上 CI。现在设一个环境变量就能把整个程序关进一个目录里：

```bash
export LINUXWAVE_TEST=~/.test/linuxwave
wave install tree
```

程序会把 `~/.test/linuxwave` **当作 `/`**：

| 平时 | 测试模式下 |
| --- | --- |
| `/etc/linuxwave_config` | `~/.test/linuxwave/etc/linuxwave_config` |
| `$HOME` | `~/.test/linuxwave/home/<你>` |
| `~/.config/linuxwave_config` | `~/.test/linuxwave/home/<你>/.config/linuxwave_config` |

要点：

- **没设 `LINUXWAVE_TEST` 时行为一个字节都不变**（shell 侧靠 `SYS_ROOT=""`，`"$SYS_ROOT/etc/..."` 就还是 `"/etc/..."`）。
- Python 侧所有绝对路径都从 `lib/configpaths.py` 的 `rooted()` 出，所以只改一处。
- `install.sh` / `selfupdate.sh` / `uninstall.sh` 可能被 `curl` 直接执行，拿不到 Python 的变量，所以它们各自解析一遍，并导出 `LINUXWAVE_TEST_ROOT` 给下游。
- 被 Python 调用的那些 shell（`depsmanager.sh`、`transfer.sh`、`pkgunzip.sh`）不用改：它们的路径来自 `BASE_DIR`，且继承重定向后的 `HOME`。

⚠️ **没设这个变量时不要跑随机化的端到端回归** —— 它会真装真删。

## Shared installs: say how to make the group take effect, right at the end of the install

Before 3.0.2 the installer only mentioned "re-login after joining the group" when something
had already failed. On a systemd desktop a re-login often is not enough, which leaves users
convinced the install is broken.

The reason: the processes of a graphical session (the shell, terminals, editors) are usually
started by `systemd --user`, the per-user manager, rather than by the login session itself.
It can outlive a logout — especially when you log back in quickly, at which point systemd
cancels the teardown — and so keeps holding the credential set from **before** you joined the
group. The tree stays unwritable even after a re-login, because the parent never changed.

As of 3.0.2 three places point at the next step:

- `lib/install.sh` — the **end-of-install summary** (new here, so nobody has to hit the error first)
- `lib/selfupdate.sh` — the self-update summary (a shared tree is handed to the group there too)
- `pkg/pkginstaller.py` — `print_write_permission_advice()`, the message you see on failure

If the tree is still unwritable after a re-login, the user manager started at your first login
is holding the old credentials. Run

```
systemctl --user exit
```

and log in again (a reboot does the same).

This is not a new idea: `lib/uninstall.sh` already used the same move when removing the
dedicated `linuxwave` account (`systemctl stop user@<uid>.service`, without which `userdel`
refuses because the account is still in use).

The shared-install notes on the website and in both READMEs carry the same sentence now.

## New: run the whole thing inside a fake root (`LINUXWAVE_TEST`)

An end-to-end run installs packages, rewrites config and deletes directories, so it used to be
CI-only. One environment variable now fences the whole program into a single directory:

```bash
export LINUXWAVE_TEST=~/.test/linuxwave
wave install tree
```

The program treats `~/.test/linuxwave` as **`/`**:

| Normally | Under the test root |
| --- | --- |
| `/etc/linuxwave_config` | `~/.test/linuxwave/etc/linuxwave_config` |
| `$HOME` | `~/.test/linuxwave/home/<you>` |
| `~/.config/linuxwave_config` | `~/.test/linuxwave/home/<you>/.config/linuxwave_config` |

Notes:

- **Without the variable, not one byte of behaviour changes** (the shell side relies on
  `SYS_ROOT=""`, so `"$SYS_ROOT/etc/..."` is still `"/etc/..."`).
- On the Python side every absolute path comes from `rooted()` in `lib/configpaths.py`, so
  there is a single place to change.
- `install.sh` / `selfupdate.sh` / `uninstall.sh` can be executed straight from `curl` and never
  see Python's variables, so each resolves the root itself and exports `LINUXWAVE_TEST_ROOT`
  for whatever it spawns.
- The shells that Python drives (`depsmanager.sh`, `transfer.sh`, `pkgunzip.sh`) need no change:
  their paths come from `BASE_DIR`, and they inherit the redirected `HOME`.

⚠️ **Do not run the randomized end-to-end regression without the variable** — it really
installs and really deletes.

## Also included: the MacWave 3.0.2 follow-up and two fixes

`main` and `3.0` are kept in sync automatically, so this release also carries changes merged
earlier:

- **MacWave 3.0.2 follow-up** (`b6acc56`): the `--ver=V` spelling, the name/version whitelist,
  the "final path must stay inside the install tree" checks, the shell-side backstop in
  `depsmanager.sh`, and `GH_TOKEN`/`GITHUB_TOKEN` being sent to `api.github.com` to soften the
  unauthenticated rate limit
- **`assert_inside_entry()`**: the containment check no longer follows the final symlink, so
  `wave link` / `unlink` / `uninstall` are not mistaken for escapes
- **Symlinked libraries in the dependency-tree index** (`a886057`): conda libraries routinely
  ship `libfoo.so.1` as a symlink to `libfoo.so.1.2.3`; matching only `-type f` dropped it from
  the index, so such a reference was misreported as external
