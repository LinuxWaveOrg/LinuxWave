# LinuxWave 3.0.3

Build number: **285A2127**

**本次为兼容更新：3.0.2 装过的用户可以直接 `wave selfupdate` 升到 3.0.3，不需要重装。**

## 性能：ELF 重定位从「二十分钟」回到「十六秒」

MacWave 在 3.0.4 里修掉的重定位性能问题，LinuxWave 这条路径上**三个原因一个不缺**。
它们叠在一起：装一个带依赖链的包，光在路径替换这一步就要等二十分钟量级。

### 实验数据

基准：18 个依赖树、**14151** 个文件、19 个 target（18 个依赖目录 + 1 个软件包目录），
树里放 **92 个真实 ELF**（真实 `libidn2` / `libunistring` 载荷 + 真实 `wget` 二进制）。
规模按真实形态对齐——依赖树里绝大多数是头文件、文档、man page，真正的 ELF 只占少数，
而不是几十个 ELF 堆在一起（后者会让 `patchelf` 本身盖过索引开销，把差别冲淡）。

| 阶段 | 耗时 | 相对改造前 |
| --- | --- | --- |
| 改造前 | **20 分 49 秒** | 1× |
| 索引只建一次 + 去掉逐文件 fork | **1 分 52 秒** | 11.1× |
| ELF 检测移出逐文件循环 | **16.08 秒** | **77.7×** |

最后两行都走完整的 `patchelf --print-rpath` / `--set-rpath` / `--print-needed` 流程，
没有跳过任何 ELF。三份产物（改造前 / 中间态 / 改造后）的 **92 个 ELF，RUNPATH 逐条一致**——
逐文件比对 `patchelf --print-rpath` 的输出，不是"抽几个看看"。加速没有牺牲功能。

### 三个原因

**1. 依赖侧索引对每个 target 重建（O(n²)）**

统一收尾会对**每个**已安装依赖各调一次 `transfer.sh`，而每次内部都要把**全部**依赖树
重新扫一遍建索引 —— 18 个依赖就是 18 × 18 = **324 次全树扫描**。这是二十分钟的主要来源。
依赖侧的内容（整棵依赖树的名字表、依赖 `lib/` 里的库名）对所有 target 完全相同，
现在由调用方给一个共享索引目录，**只建一次**，其余 target 复用。

**2. 建索引时逐文件 fork `basename` + 反复开关文件**

`basename "$file" >> "$MAP_FILE"` 每个文件一次 fork 加一次开/关文件；上万文件时这一项
本身就压过一切。现在取名字用 shell 内建 `${file##*/}`、输出用内建 `printf`，重定向移到循环外，
整棵树一次写完。

**3. 每个文件 fork 三个进程判断是不是 ELF**

`magic="$(head -c 4 "$file" | od -An -tx1 | tr -d ' \n')"` 每文件 3 次 fork。
现在**一次 Python 扫描**按魔数列出全部 ELF，只对这些文件调 `patchelf`；
`python3` 不可用时自动退回原来的逐文件做法。

此外，每个未解析符号原本要 fork 两次 `grep`（查 `PROVIDED` 与 `SYSTEM` 两张表），
现在两张表连同 `TREE` 一起装进关联数组，纯查表、零 fork。

### 行为没有变化

- 解析顺序不变：产物自己的 `lib/` → `_DEPS` 声明的依赖 → 其它已安装依赖兜底；
- 软链接仍被排除在重定位之外（`find -type f` 的语义用 `os.lstat` + `S_ISREG` 对齐）；
- 非 ELF（静态库 `!<arch>`、脚本、数据文件）、悬空链接、无 `.dynamic` 的 ELF 行为不变；
- 不给第三个参数时行为与改造前完全一致（只是仍用内建取名字）；
- 落盘结果幂等，重复执行零副作用。

### 排查中的一个坑

共享索引是**跨 target 复用**的，所以它的内容必须与"哪个 target 在跑"无关。
第一版让依赖侧的名字表从**去重后的库目录表**派生，而那张表会把"本 target 自己"的
`lib/` 剔掉（它已经在解析顺序里了）——于是缓存一旦由第一个 target 建出来，
**它自己 lib 里的库名就永久缺席**，后面每个 target 都会把本该接得上的引用报成
「存在但接不上」。

它没有在测试里暴露，因为那台机器的 `ldconfig` 恰好登记了 `libidn2` / `libunistring`，
系统库豁免把误报吃掉了。改用独立扫 `deps/*/*` 之后缓存才与 target 无关；
为了证明这条路径，反向验证过一次：手工把缓存"投毒"成漏掉 `libidn2` 的版本，
误报立刻复现。

## Performance: ELF relocation is back to sixteen seconds

The relocation performance problem MacWave fixed in 3.0.4 has **all three of its causes**
on the LinuxWave side too. Stacked together, they made installing a package spend the
order of twenty minutes in the path-rewriting step alone.

### Measurements

Benchmark: 18 dependency trees, **14151** files, 19 targets (18 dependency directories
plus one package directory), with **92 real ELF files** in the tree (real `libidn2` /
`libunistring` payloads plus the real `wget` binary). The shape is aligned with reality --
dependency trees are overwhelmingly headers, docs and man pages with only a handful of real
ELF files, rather than dozens of ELF files piled together (the latter lets `patchelf` itself
drown out the indexing cost and washes the difference out).

| Stage | Time | vs. before |
| --- | --- | --- |
| Before | **20m49s** | 1× |
| Index built once, no per-file forks | **1m52s** | 11.1× |
| ELF detection out of the per-file loop | **16.08s** | **77.7×** |

The last two rows go through the complete `patchelf --print-rpath` / `--set-rpath` /
`--print-needed` flow and skip no ELF file at all. Across three build products
(before / intermediate / after) the **92 ELF files have byte-identical RUNPATHs** --
compared file by file against `patchelf --print-rpath` output, not spot-checked.
The speedup does not come at the cost of correctness.

### Three causes

**1. The dependency-side index was rebuilt for every target (O(n²))**

The final pass runs `transfer.sh` once per installed dependency, and every run rebuilt the
index over *every* dependency tree -- with 18 dependencies that is 18 × 18 = **324 full tree
walks**. That was the bulk of the twenty minutes. The dependency-side content (the name table
of the whole tree, and the library names inside dependency `lib/` directories) is identical
for every target, so the caller now hands down a shared index directory: it is built **once**
and reused by the remaining targets.

**2. Building the index forked `basename` and reopened the output file per entry**

`basename "$file" >> "$MAP_FILE"` costs one fork plus one open/close per file; with tens of
thousands of files that alone dominates everything else. Name extraction now uses the shell
builtin `${file##*/}`, output uses the builtin `printf`, and the redirect sits outside the
loop so a whole tree is written in one go.

**3. ELF detection forked three processes per file**

`magic="$(head -c 4 "$file" | od -An -tx1 | tr -d ' \n')"` is three forks per file.
A single Python pass now lists every ELF by magic number, and only those are handed to
`patchelf`; when `python3` is unavailable it falls back to the old per-file check.

On top of that, every unresolved symbol used to cost two `grep` forks (one against the
`PROVIDED` table, one against `SYSTEM`). Both tables -- and `TREE` as well -- now live in
associative arrays, so lookups fork nothing at all.

### Behaviour is unchanged

- the resolution order is unchanged: the artefact's own `lib/`, then the dependencies
  declared in `_DEPS`, then every other installed dependency as a fallback;
- symlinks are still excluded from relocation (the `find -type f` semantics are matched with
  `os.lstat` + `S_ISREG`);
- non-ELF files (static archives `!<arch>`, scripts, data files), dangling links and ELFs
  without `.dynamic` behave exactly as before;
- without the third argument the behaviour is identical to before (minus the forks);
- the result is idempotent: running it twice changes nothing.

### One pitfall found on the way

The shared index is **reused across targets**, so its contents must not depend on which target
is running. The first version derived the dependency-side name table from the *deduplicated*
library directory list, and that list drops "this target's own `lib/`" (it already sits in the
resolution order) -- so once the cache was built by the first target, **that target's own
library names were permanently missing from it**, and every later target reported references
that could actually be satisfied as "present but not linked".

It did not show up in testing because that machine's `ldconfig` happened to list `libidn2`
and `libunistring`, and the system-library exemption swallowed the false report. Deriving the
cache from an independent scan of `deps/*/*` makes it target-independent; to prove the path,
the cache was deliberately poisoned with the earlier version and the false report reappeared
immediately.

## 依赖审计立刻抓到两个数据缺口

这一版给 CI 加上了「装完每个带依赖的包之后跑一次 `audit_deps.py edges`」，
把数据声明与实测 `DT_NEEDED` 对照。**第一次跑就红了**，而且抓到的是真问题。

### 缺口一：`libidn2` 少了 `libiconv`（真缺口）

```
✗ libidn2@2.3.8 实际引用了 libiconv，但数据里没有声明
```

`libidn2.so.0.4.0` 的 `DT_NEEDED` 里有 `libiconv.so.2`，而数据里只声明了 `libunistring`。
glibc 的 iconv 在 libc 里，发行版不带 GNU libiconv，所以这个引用**没法由系统兜底**：

```
$ wave install libidn2
$ libidn2@2.3.8/bin/idn2 --version
libidn2@2.3.8/bin/idn2: error while loading shared libraries:
libiconv.so.2: cannot open shared object file: No such file or directory
```

现状之所以没暴露，是因为唯一声明 `libidn2` 的包 `wget` 自己也声明了 `libiconv`，属于巧合。
amd64 与 arm64 两个载荷都核对过，都有这一条，数据侧已补上（`libiconv@1.18`）。

### 缺口二：审计自己过严（`zstd` → `xz` 是误报）

把全部 15 个依赖都装齐之后再跑，又冒出一条：

```
✗ zstd@1.5.7 实际引用了 xz，但数据里没有声明
```

这条是**误报**：`liblzma.so.5` 系统本来就有（`ldconfig -p` 里查得到），只是 `xz`
这个依赖也提供同名库，于是被算成了漏声明。实测只装 `zstd`、不装 `xz`：

```
$ zstd --version
*** Zstandard CLI (64-bit) v1.5.7, by Yann Collet ***
```

`zstd` 同样依赖系统的 `libz.so.1` 与 `liblz4.so.1`，而**没有任何依赖提供这两个名字**，
所以它本来就不可能自给自足——单要求它声明 `xz` 并不自洽。审计的判据于是改成：
**只有系统给不了的引用才算漏声明**。而「已声明但实测没引用」的提醒仍按全部引用判定，
不受该豁免影响（否则 `libunistring`、`libcrypto` 这类系统也有的库会被误报成"没引用"）。

### 顺带：`zlib` 依赖其实不提供可用的 `libz.so.1`

`zlib@1.3.2` 载荷里只有 `lib/libz.a` 和一个**悬空**的 `lib/libz.so -> libz.so.1.3.2`
（`libz.so.1.3.2` 不在包里）。也就是说声明了 `zlib` 的包（`wget`、`libxml2`、`pcre2`）
拿不到运行期可用的 libz，一直靠系统的 `libz.so.1`。**本次没有改它**——
换包会改变依赖集合与版本，值得单独评估；这里先记录。

### 顺带：`deps_test.sh` 的版本开关不该统一

改成"覆盖所有带依赖的包"之后，`tmux` 立刻红了：它在 `--version` 下不报版本，
tmux 用的是 `-V`。现在逐个试 `--version` / `-V` / `-v` / `version`，能跑起来就算过——
加载不到库时任何参数都会以退出码 127 失败，不会被这一步放过。

## The dependency audit immediately found two data gaps

This version adds "run `audit_deps.py edges` after installing every package that has
dependencies" to CI, comparing the declared data against the measured `DT_NEEDED` entries.
**It went red on the first run**, and what it caught was real.

### Gap one: `libidn2` was missing `libiconv` (real)

```
✗ libidn2@2.3.8 实际引用了 libiconv，但数据里没有声明
```

`libidn2.so.0.4.0` has `libiconv.so.2` in its `DT_NEEDED`, while the data declares only
`libunistring`. glibc carries iconv inside libc and distributions do not ship GNU libiconv,
so **the system cannot satisfy that reference**:

```
$ wave install libidn2
$ libidn2@2.3.8/bin/idn2 --version
libidn2@2.3.8/bin/idn2: error while loading shared libraries:
libiconv.so.2: cannot open shared object file: No such file or directory
```

It stayed hidden because the only package declaring `libidn2` -- `wget` -- happens to declare
`libiconv` itself. Both the amd64 and arm64 payloads were checked and both carry the entry;
the data now declares `libiconv@1.18`.

### Gap two: the audit itself was too strict (`zstd` → `xz` is a false positive)

Installing all 15 dependencies and auditing again surfaced one more:

```
✗ zstd@1.5.7 实际引用了 xz，但数据里没有声明
```

That one is a **false positive**: `liblzma.so.5` is on the system anyway (it is listed by
`ldconfig -p`); it was counted as a missing declaration only because the `xz` dependency also
ships a library of that name. Measured with `zstd` installed on its own, no `xz`:

```
$ zstd --version
*** Zstandard CLI (64-bit) v1.5.7, by Yann Collet ***
```

`zstd` also needs the system `libz.so.1` and `liblz4.so.1`, and **no dependency provides
either name**, so it can never be self-contained -- demanding a declaration for `xz` alone is
not consistent. The audit's criterion is now: **only references the system cannot satisfy
count as missing declarations**. The "declared but not referenced" warning still uses the full
reference set, unaffected by the exemption (otherwise libraries the system also provides, such
as `libunistring` and `libcrypto`, would be reported as "not referenced").

### Aside: the `zlib` dependency provides no usable `libz.so.1`

The `zlib@1.3.2` payload contains only `lib/libz.a` and a **dangling**
`lib/libz.so -> libz.so.1.3.2` (there is no `libz.so.1.3.2` in the package). So packages
declaring `zlib` (`wget`, `libxml2`, `pcre2`) get no runtime libz from the tree and have always
relied on the system's `libz.so.1`. **This release does not change it** -- switching packages
would alter the dependency set and versions, and deserves its own evaluation. Recorded here.

### Aside: the test's version flag should not be uniform

Once the dependency test covered *every* package with dependencies, `tmux` went red
immediately: it does not report its version under `--version`, tmux uses `-V`. The check now
tries `--version` / `-V` / `-v` / `version` in turn and passes on the first that works --
a binary that cannot load its libraries fails under any argument with exit code 127, so this
does not let anything through.

- **归档可复现**：同样的输入重复打包，`.tar` 与 `.tar.gz` 都打出相同 SHA256。

## Verification

- **Sandbox regression**: `scripts/sandbox_test.sh` reports **139 PASS / 0 FAIL / 0 SKIP**.
  It was compared against a clean `HEAD` worktree **under the same network conditions**, and
  the two logs match line by line (the only harmless differences are the temporary directory
  name and whether a local configdata checkout is detected). One run in between showed
  130 PASS / 1 SKIP for `Ctrl-C 场景（网络抖动，未能走到下载阶段）` -- network flakiness that
  does not reproduce on a re-run, not a regression.
- **CI green**: both legs of `Format Test` pass -- **3.14 and 3.15** (the 3.15 leg is new in
  this release: `actions/python-versions` does not carry 3.15.0 yet, so it uses
  `astral-sh/setup-uv` to pull a python-build-standalone build and creates its own venv; each
  leg asserts `sys.version_info[:2]` so that the 3.15 leg cannot silently run on 3.14 and
  report green).
- **Relocation equivalence**: on the synthetic 14151-file tree the 92 ELF files have
  identical RUNPATHs across all three build products (before / intermediate / after); a
  separate 62-file tree was compared three ways (shared index / no index / before), also with
  zero differences.
- **Audit, both directions**: all 15 dependencies (**amd64 and arm64 each**) report
  `Audit passed` with exit code 0; restoring `libidn2`'s declaration to its pre-fix state
  immediately reports the `libiconv` gap on the same tree with exit code 1.
- **Batch entry point**: driven through the official fake root (`LINUXWAVE_TEST`),
  `transfer_installed_artifacts()` gives all 4 targets **the same** shared index directory,
  cleans the temporary directory up on return, and produces results identical to the
  per-target reference implementation.
- **Reproducible archives**: repacking identical input yields identical SHA256 for both
  `.tar` and `.tar.gz`.
