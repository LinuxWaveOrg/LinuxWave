# LinuxWave 3.0.5

Build number: **291G2020**

**本次为兼容更新：3.0.4 装过的用户可以直接 `wave selfupdate` 升到 3.0.5，不需要重装。**

## 修复：已经装好的依赖不该再联网

装一个带依赖链的包时，凡是**已经装过**的依赖，安装器每次都要回源取一遍它的版本文件 —— 只为拿到它自己的 `deps` 列表。而那份列表在安装时就已经写在 `<依赖目录>/_DEPS` 里了。

代价很直接：**网络一抖，一个已经装好的依赖就能让整条安装失败。**

```
wave install tmux
🌊 Dependency ncurses@6.6 is already installed, skipping.
🌊 Error: Cannot reach GitHub for the dependency data.
```

更糟的是失败时机 —— 此时软件包本体**已经落盘**，可失败发生在建「不带版本号的链接」之前，所以 `tmux` 命令用不了，用户只能整条重跑一遍。

### 修复

优先读该依赖自己落盘的 `_DEPS`；只有 `_DEPS` **不存在**时才回源，那才说明上次安装真的中断了（`_DEPS` 是安装流程的最后一步，也正因如此它才被用来判定「装完了没有」）。

`_DEPS` 每行一个 `"名字@版本"`，与写入侧的格式一一对应。传递依赖照旧递归处理，只是不再需要网络。

### 实验数据

向 `ensure_dependency` 注入「网络完全不可达」（`fetch_text` 恒返回状态码 0），装一条两个依赖都已就位的传递依赖链（`libunistring@1.4.2 → libiconv@1.18`）：

| 版本 | `fetch_text` 调用次数 | 结果 | 传递依赖是否被处理 |
| --- | --- | --- | --- |
| 修复前（3.0.4） | **1** | `report_service_unavailable` → 退出码 1 | 是 |
| 修复后（3.0.5） | **0** | 正常完成，退出码 0 | 是 |

两边都确认了 `libiconv@1.18` 仍被访问到 —— 加速没有以跳过依赖为代价。

### 影响面

- 依赖**未装**时行为完全不变（照旧下载、校验、安装）；
- 依赖**已装且 `_DEPS` 完好**时不再产生任何网络请求；
- `_DEPS` 缺失（上次中断）时仍回源补齐，不会漏装传递依赖；
- 循环依赖保护、依赖者标记（`.depped_*`）、统一收尾的路径替换都不受影响。

## Fix: an already-installed dependency no longer hits the network

When installing a package with a dependency chain, every dependency that was **already
installed** still had its version file fetched again -- just to read that dependency's own
`deps` list. That list was already written to `<dependency dir>/_DEPS` at install time.

The cost is direct: **a network hiccup on a dependency that is already installed fails the
whole install.**

```
wave install tmux
🌊 Dependency ncurses@6.6 is already installed, skipping.
🌊 Error: Cannot reach GitHub for the dependency data.
```

Worse is *when* it fails -- the package itself has **already been unpacked**, but the failure
happens before the unversioned link is created, so `tmux` is unusable and the only way forward
is to run the whole thing again.

### The fix

Read that dependency's own on-disk `_DEPS` first; only fall back to the network when `_DEPS`
is **absent**, which means the previous install really was interrupted (`_DEPS` is the last
step of the install, which is exactly why it is also used as the "is it installed" test).

`_DEPS` holds one `"name@version"` per line, matching the writer. Transitive dependencies are
still followed recursively -- there is simply no network involved any more.

### Measurements

"Network completely unreachable" was injected into `ensure_dependency` (`fetch_text` always
returns status 0) while installing a transitive chain whose two dependencies were both already
in place (`libunistring@1.4.2 → libiconv@1.18`):

| Version | `fetch_text` calls | Result | Transitive dependency handled |
| --- | --- | --- | --- |
| Before (3.0.4) | **1** | `report_service_unavailable` → exit 1 | yes |
| After (3.0.5) | **0** | completed, exit 0 | yes |

Both runs confirmed `libiconv@1.18` was still visited, so the speedup does not come from
skipping dependencies.

### Impact

- a dependency that is **not installed** behaves exactly as before (download, checksum, install);
- an **installed dependency with an intact `_DEPS`** triggers no network request at all;
- a **missing `_DEPS`** (interrupted install) still falls back to the network, so no transitive
  dependency is missed;
- cycle protection, depender markers (`.depped_*`) and the final relocation pass are unaffected.

## 验证

- **对照实验**：上表两组实测，`fetch_text` 调用次数 1 → 0，退出码 1 → 0，传递依赖两侧都处理
- **沙箱回归**：`scripts/sandbox_test.sh` **139 PASS / 0 FAIL / 0 SKIP**，与改动前逐条一致
- **CI 全绿**：`Format Test` 两条腿（Python 3.14 与 3.15）全部通过，含新增的 `Run checksum test`
- **发布分支同步**：`Sync main with the release branch` 在 `protect-all-branches` 规则集生效后
  用 `RELEASE_SYNC_TOKEN` 真实推送成功（`main` 与 `3.0` 均指向同一提交）
